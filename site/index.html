ROS 2 rolling · emscripten-wasm32 · rmw_zenoh_pico

A real ROS 2 node,
compiled to WebAssembly.

Not a JavaScript re-implementation, not a bridge to a native process running somewhere else — an actual rclpy node, with real numpy and a real CPython interpreter, cross-compiled to wasm32 and speaking zenoh from inside your browser tab. No pthreads, no Asyncify — a single wasm32 thread, cooperatively retrying instead of blocking.

What this is

Cross-compiling the actual ROS 2 stack, not a lookalike

Most "ROS 2 in the browser" demos work by running a JavaScript client (roslibjs) that speaks the rosbridge_websocket protocol to a normal, native ROS 2 process running elsewhere — the browser never runs any ROS 2 code itself. This is different: every binary here was built by RoboStack's conda-based ROS 2 build pipeline, targeting emscripten-wasm32 as a first-class platform, and runs entirely client-side.

rclc & rclcpp rclpy + numpy single-threaded — no pthreads, no Asyncify rmw_zenoh_pico zenoh over WebSocket ~230 packages cross-built
01
No threads. Blocking on a real OS-style thread isn't an option in a plain (non-Asyncify, non-pthreads) wasm32 build — so nothing here ever blocks. Every network call (zenoh-pico's WebSocket transport, underneath rmw_zenoh_pico) makes exactly one non-blocking attempt and returns immediately; retrying is driven from outside the wasm module instead — a JS interval ticking a poll function for the C/C++ demos, Python's own await asyncio.sleep() loop for rclpy and the notebook.
02
Transport. rmw_zenoh_pico gives ROS 2's standard rcl/rclcpp/rclpy layers a wasm-friendly RMW backed by zenoh-pico's WebSocket transport — talking to a normal zenohd router, not a custom protocol.
03
Python. A stock, unmodified emscripten-forge CPython and numpy — no custom build needed, since nothing here relies on real OS threads anymore. rclpy's own extension module, each message package's typesupport accessor, and numpy's C extensions are dlopen'd the normal way, by Python's own import machinery, not statically pre-registered.
04
Not just browsers. zenoh-pico and rmw_zenoh_pico exist to put ROS 2 on genuinely constrained targets — microcontrollers talking micro-ROS over UART, BLE, or serial, the same niche as the ESP32/STM32-class boards this stack was originally built for. Wasm32 is really just one more "small, sandboxed target" for the exact same lightweight client; the C talker below would cross-compile to an actual microcontroller with far fewer changes than it took to get it running in a browser tab.

Live demos

Run them yourself

Both demos publish a ROS 2 topic once a second from inside a wasm32 sandbox running in this tab — but only once they can actually reach a zenoh router: the wasm build connects to 127.0.0.1:7447 (a loopback address, so your browser will let an https page reach it even without a certificate). Start the router below first, then click "Run demo" — without one reachable, the node still boots and keeps retrying the connection (visible in the console) rather than publishing, until one shows up.

Do this first — run a local zenoh router:

zenohd is a plain conda-forge package — pixi's exec installs it into a throwaway environment and runs it in one line, no ROS or project directory needed (just pixi itself). This also enables the router's REST admin API, which the "Live ROS graph" panel below uses to show what's actually on the graph in real time — entirely optional, the demos work fine without it too:

pixi exec --with zenohd --with zenoh-plugin-rest -c conda-forge -- bash -c '
ext=so; [ "$(uname)" = "Darwin" ] && ext=dylib
zenohd -l ws/127.0.0.1:7447 --no-multicast-scouting \
  -P "rest:$(dirname $(which zenohd))/../lib/libzenoh_plugin_rest.$ext" --rest-http-port 8000'

Once it's up, just click "Run demo" below — no page reload needed.

Reaching the router from a different machine (phone, another laptop, a Pi, ...)

That other machine's 127.0.0.1 is itself, not your desktop — so it needs your desktop's real address. If the other machine is running a browser (a phone for the GPS/tilt demos, or this same page open somewhere else): since this page is served over https://, browsers block a plain ws:// connection to anything but 127.0.0.1/localhost (mixed content), so it needs TLS too. Caddy (also on conda-forge) terminates that in one more line, with a self-signed cert it generates on the fly — no cert files to manage. Run the router (same command as above, just on a different port so Caddy can sit in front of it):

pixi exec --with zenohd -c conda-forge zenohd -l ws/127.0.0.1:17447 --no-multicast-scouting

Then, in a second terminal:

pixi exec --with caddy --with python -c conda-forge bash -c 'printf "{\n\tskip_install_trust\n}\nhttps://%s:7443 {\n\treverse_proxy :17447\n}\n" "$(python -c "import socket;s=socket.socket(socket.AF_INET,socket.SOCK_DGRAM);s.connect((\"8.8.8.8\",80));print(s.getsockname()[0])")" | caddy run --config - --adapter caddyfile'

The inner python call just asks the OS which network interface it would route through — same trick works on macOS, Linux and Windows, no guessing interface names. skip_install_trust stops Caddy from prompting for your password to install its cert into your desktop's own trust store — unnecessary here, since it's your phone that needs to trust it, not the desktop. Caddy logs the exact address it's proxying from (something like 192.168.1.50:7443) — that's what goes in the "zenoh router" field on the demo page, with the "wss (TLS)" box checked.

One manual step, unavoidable for a self-signed cert: open https://<that address>/ directly on the phone once first and accept the browser's "not private" warning — after that, the demo page's wss:// connection to the same address will work.

If the other machine is running a native process instead of a browser — e.g. the ros2 topic echo verification below, or a real ROS 2 node — skip all of the above: mixed-content and TLS are browser-only rules, so a plain listener on your LAN address is enough. Add it as a second listener on the same router (same command as the very first box, just with an extra -l):

pixi exec --with zenohd -c conda-forge zenohd -l ws/127.0.0.1:7447 -l tcp/0.0.0.0:7448 --no-multicast-scouting

Then point the other machine's connect.endpoints (in the ZENOH_SESSION_CONFIG_URI config below) at tcp/<your desktop's LAN address>:7448 instead of ws/127.0.0.1:7447 — no Caddy, no cert, one extra flag.

Want independent proof this is really ROS 2, not just a browser animation? Verify with a native ros2 CLI

Same trick as the router above — pixi exec installs a throwaway RoboStack ROS 2 rolling environment (with rmw_zenoh_cpp, the native peer to this demo's rmw_zenoh_pico) and points it at the same router, no install left behind. Run this while a demo above is running — it echoes the actual messages arriving from the wasm32 node, decoded by a completely separate, native process that never touched a browser:

pixi exec -c https://prefix.dev/robostack-rolling -c conda-forge --spec ros-rolling-ros-base --spec ros-rolling-rmw-zenoh-cpp -- bash -c '
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
export ZENOH_SESSION_CONFIG_URI=$(mktemp -t zenohcfg).json5
echo "{mode:\"client\",connect:{endpoints:[\"ws/127.0.0.1:7447\"]},scouting:{multicast:{enabled:false}}}" > "$ZENOH_SESSION_CONFIG_URI"
ros2 topic echo /chatter'

Swap /chatter for /chatter_rclpy to listen to the rclpy talker instead. Both should print a fresh data: 'Hello from wasm32 ...' line every second.

How fast is this, really?

Measured throughput, not just "it works"

The demos above publish at a deliberately modest, battery-friendly rate — but how much headroom is actually there? Measured with a native ros2 topic hz / ros2 topic bw (the same native verification tooling above) against a local router, temporarily patching the camera demo's own publish rate to find where it actually breaks down, then reverting — nothing below is shipped code, just a benchmarking pass.

ConfigurationMeasured rateBandwidth
rclc talker (as deployed)2.0 Hz~105 B/s (52 B std_msgs/String)
Camera demo (as deployed)10.0 Hz~23 KB/s (~2.3 KB JPEG)
Camera, timer pushed to 200 Hz200 Hz (exact)~420 KB/s
Camera, timer pushed to 1000 Hz*plateaus at ~250 Hz~500 KB/s
Camera, 1000 Hz + MessageChannel tick loop~1000 Hz (exact)~2.2 MB/s
Camera, uncapped timer + MessageChannel~4700 Hz (ceiling)~10–11 MB/s

*The 250 Hz plateau despite requesting 1000 Hz is a real, well-known browser quirk, not a zenoh/ROS 2 limit: browsers clamp setInterval/setTimeout to a ~4 ms floor (1000 ms / 4 ms = 250) — exactly what was measured. Rescheduling the tick via a MessageChannel postMessage loop (a standard technique for sub-4 ms callback scheduling in browsers) removes that ceiling entirely, scaling cleanly to the requested rate all the way up to ~4700 Hz, where rcl_publish() + zenoh-pico's WebSocket write + the full round trip to a native subscriber finally becomes the real bottleneck — still around 10 MB/s for ~2 KB messages. In short: the current 2–10 Hz demo rates are a deliberate UX/battery choice with roughly three orders of magnitude of headroom underneath, not a sign this architecture is slow.

Known limitations

  • rmw_zenoh_pico doesn't support publisher/subscriber QoS event callbacks yet — the demo nodes disable them explicitly rather than hitting an unhandled error.
  • Its TypeDescriptionService isn't implemented either (would hang, not error) — disabled in the same way; parameter and rosout services are switched off at node construction for the same reason.
  • The rclc-based demos' zenoh connect address is runtime-configurable now (a "zenoh router" field on each page, or ?zenoh_host=&zenoh_port=&zenoh_tls=1 in the URL) via rmw_zenoh_pico_set_unicast(), with a wss:// option for reaching a router on a different device (see the setup box's phone section) — but the rclpy talker above still only connects to the compiled-in default (127.0.0.1:7447).
  • The literal blocking rclpy.spin(node) can't work in this build — it's a synchronous loop with no yield point, and with no pthreads and no Asyncify there's no way to let the browser's event loop run a WebSocket callback while a single synchronous call is still on the stack, so it would just freeze the tab forever. The notebook below uses a spin_async() helper instead — the same non-blocking spin_once() every demo here already uses, looped behind await asyncio.sleep() as a background task.

Every change, upstream

Nothing here is a fork-and-hack — every piece needed to make this work was written as a normal pull request against the project it belongs to. The full write-up, with rationale for each one, lives in this repo's README.

RepoWhat changed
vinca #154 RoboStack's cross-platform recipe generator: makes emscripten-wasm32 a fully non-blocking, single-threaded ament_cmake build target (no pthreads, no Asyncify) and fixes a MODULE vs. SHARED CMake flag mismatch that only shows up when targeting emscripten.
ros-rolling #46 The actual recipe pipeline change: adds emscripten-wasm32 as a target platform for ROS 2 rolling and wires up rmw_zenoh_pico, producing the ~230 packages these demos are built from.
zenoh-pico #1314 Rewrites zenoh-pico's emscripten/wasm32 transport (session open, read, send) to make exactly one non-blocking attempt per call instead of blocking or internally sleeping-and-retrying — needed once real threads were off the table.
rmw_zenoh_pico #7 Fixes and gaps in the RMW layer itself, hit while getting a full rclcpp/rclpy node (not just zenoh-pico's own pub/sub API) working end-to-end — including the non-blocking, resumable session-open state machine and the cooperative-polling rewrite of rmw_wait() that this whole no-threads approach depends on.

rosidl_typesupport_microxrcedds #83 Typesupport codegen fixes hit while cross-building the message packages this demo depends on.
