What this is

Cross-compiling the actual ROS 2 stack, not a lookalike

Most "ROS 2 in the browser" demos work by running a JavaScript client (roslibjs) that speaks the rosbridge_websocket protocol to a normal, native ROS 2 process running elsewhere — the browser never runs any ROS 2 code itself. This is different: every binary here was built by RoboStack's conda-based ROS 2 build pipeline, targeting emscripten-wasm32 as a first-class platform, and runs entirely client-side.

rclc & rclcpp rclpy + numpy real pthreads (SharedArrayBuffer) rmw_zenoh_pico zenoh over WebSocket ~230 packages cross-built
01
Threads. Emscripten's libc++ needs a real OS-style thread to ever wake a blocked condition_variable — so every package here is built with actual wasm32 threads (-pthread, SharedArrayBuffer), not the single-threaded default.
02
Transport. rmw_zenoh_pico gives ROS 2's standard rcl/rclcpp/rclpy layers a wasm-friendly RMW backed by zenoh-pico's WebSocket transport — talking to a normal zenohd router, not a custom protocol.
03
Python. Stock emscripten-forge Python isn't pthread-enabled. This demo uses a custom CPython (--enable-wasm-pthreads) and a pthreads-patched numpy, with every extension module registered ahead-of-time via PyImport_AppendInittab instead of relying on runtime dlopen.
04
Not just browsers. zenoh-pico and rmw_zenoh_pico exist to put ROS 2 on genuinely constrained targets — microcontrollers talking micro-ROS over UART, BLE, or serial, the same niche as the ESP32/STM32-class boards this stack was originally built for. Wasm32 is really just one more "small, sandboxed target" for the exact same lightweight client; the C talker below would cross-compile to an actual microcontroller with far fewer changes than it took to get it running in a browser tab.

Live demos

Run them yourself

Both demos publish a ROS 2 topic once a second from inside a wasm32 sandbox running in this tab — but only once they can actually reach a zenoh router: the wasm build connects to 127.0.0.1:7447 (a loopback address, so your browser will let an https page reach it even without a certificate). Start the router below first, then click "Run demo" — without one reachable, the node still boots and attempts the connection (visible in the console), but exits shortly after rather than looping.

Do this first — run a local zenoh router:

zenohd is a plain conda-forge package — pixi's exec installs it into a throwaway environment and runs it in one line, no ROS or project directory needed (just pixi itself):

pixi exec --with zenohd -c conda-forge zenohd -l ws/127.0.0.1:7447 --no-multicast-scouting

Once it's up, just click "Run demo" below — no page reload needed.

Testing from a phone instead? The GPS/tilt demos need a router your phone can actually reach

Your phone's 127.0.0.1 is the phone itself, not your desktop — so it needs your desktop's real address. And since this page is served over https://, browsers block a plain ws:// connection to anything but 127.0.0.1/localhost (mixed content), so it needs TLS too. Caddy (also on conda-forge) terminates that in one more line, with a self-signed cert it generates on the fly — no cert files to manage. Run the router (same command as above, just on a different port so Caddy can sit in front of it):

pixi exec --with zenohd -c conda-forge zenohd -l ws/127.0.0.1:17447 --no-multicast-scouting

Then, in a second terminal:

pixi exec --with caddy --with python -c conda-forge bash -c 'printf "{\n\tskip_install_trust\n}\nhttps://%s:7443 {\n\treverse_proxy :17447\n}\n" "$(python -c "import socket;s=socket.socket(socket.AF_INET,socket.SOCK_DGRAM);s.connect((\"8.8.8.8\",80));print(s.getsockname()[0])")" | caddy run --config - --adapter caddyfile'

The inner python call just asks the OS which network interface it would route through — same trick works on macOS, Linux and Windows, no guessing interface names. skip_install_trust stops Caddy from prompting for your password to install its cert into your desktop's own trust store — unnecessary here, since it's your phone that needs to trust it, not the desktop. Caddy logs the exact address it's proxying from (something like 192.168.1.50:7443) — that's what goes in the "zenoh router" field on the demo page, with the "wss (TLS)" box checked.

One manual step, unavoidable for a self-signed cert: open https://<that address>/ directly on the phone once first and accept the browser's "not private" warning — after that, the demo page's wss:// connection to the same address will work.

Known limitations

  • rmw_zenoh_pico doesn't support publisher/subscriber QoS event callbacks yet — the demo nodes disable them explicitly rather than hitting an unhandled error.
  • Its TypeDescriptionService isn't implemented either (would hang, not error) — disabled in the same way; parameter and rosout services are switched off at node construction for the same reason.
  • The rclc-based demos' zenoh connect address is runtime-configurable now (a "zenoh router" field on each page, or ?zenoh_host=&zenoh_port=&zenoh_tls=1 in the URL) via rmw_zenoh_pico_set_unicast(), with a wss:// option for reaching a router on a different device (see the setup box's phone section) — but the rclpy talker above still only connects to the compiled-in default (127.0.0.1:7447).
